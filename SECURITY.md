# Обновление безопасности

Перед развёртыванием сделайте резервную копию MySQL и тома `uploads`.

- Примените `pnpm db:migrate` (в Docker это делает entrypoint). Миграция `0025_auth_session_version` добавляет версию сессий. Старые JWT перестают приниматься: пользователи входят повторно с прежними паролями. SHA-256 хеши переводятся на scrypt при успешном входе; сброс паролей не требуется.
- Выход отзывает все сессии данного пользователя. Смена/сброс пароля также отзывает все сессии; после самостоятельной смены текущему браузеру выдаётся новый токен.
- Для первой установки задайте уникальный `ADMIN_PASSWORD` (12–128 символов) и случайный `JWT_SECRET` (не менее 32 символов). Например, `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`. Не публикуйте сгенерированные значения. `LOGIN_INFO.txt` удалён и не используется. Если старые секреты уже раскрывались, замените их отдельно.
- Заполните уникальные `MYSQL_ROOT_PASSWORD` и `MYSQL_PASSWORD`. Для существующей БД смена значения в `.env` сама по себе не меняет пароль в MySQL: ротацию выполняют согласованно в БД и конфигурации приложения.
- Укажите `WIDGET_ALLOWED_ORIGINS` списком точных HTTPS-origin сайтов. Пустое значение в production запрещает стороннее встраивание. `*` разрешает любой сайт; CORS не заменяет аутентификацию и ограничения API.
- Bitrix24 должен передавать `Authorization: Bearer <BITRIX24_INBOUND_SECRET>`. Без отдельного секрета длиной от 32 символов входящий webhook отключён. Не используйте исходящий webhook URL в качестве этого секрета.
- `TRUST_PROXY=true` означает один доверенный reverse proxy. Он должен добавлять реальный IP клиента справа в `X-Forwarded-For`; прямой доступ к приложению из интернета закройте. Схема с несколькими прокси требует отдельной настройки.
- MySQL, Weaviate и Ollama больше не публикуют порты на хост. Внутри Compose они доступны по прежним именам. Для локальной работы вне Docker используйте отдельный локальный override с привязкой портов к `127.0.0.1`.
- API скачивания документов требует вход или временную подписанную ссылку из ответа виджета (срок 1 час). Старые прямые ссылки без подписи потребуют входа. В публичную базу знаний помещайте только материалы, предназначенные посетителям: подписанные ссылки защищают от перебора ID, но ответы ассистента используют содержимое базы.
- FAQ принимает PNG/JPEG/WebP/GIF после входа администратора или редактора. Тип определяется по содержимому. Старые HTML/SVG файлы больше не отдаются.
- При включённом согласии сервер сохраняет факт принятия и версию текста в `uploads/consent-audit/YYYY-MM-DD.jsonl`, затем выдаёт подписанное подтверждение, привязанное к диалогу и origin (24 часа). Текст вопроса в этот журнал не пишется. Том `uploads` должен быть постоянным и доступным для записи только приложению; срок хранения журналов задаётся вашей эксплуатационной политикой.
- Обновляйте сервер и `chat-widget.js` вместе. После обновления замените код встраивания на актуальный из админки, чтобы обойти кеш старого скрипта.

Проверки: `pnpm check`, `pnpm test`, `pnpm build`, `pnpm audit --json`. Аудит npm проверяет JS-зависимости; он не проверяет Docker-образы, Python/OCR, ОС, firewall и конфигурацию рабочего сервера.
